## 3. QR visibility fix chain

Root cause identified 10 Sep morning: QR-bearing mails embed
`<img src="https://leena.app/api/qr-image/<uuid>">` — external image
fetches that corporate email gateways (Mailinblack, Barracuda,
Proofpoint, Exchange with "block remote content" default) strip
silently. Kawwa's report (AB Mauri behind Mailinblack, 10 Sep morning)
plus ~4 similar complaints since 7 Sep. Server-side endpoint healthy;
issue is client-side gateway policy.

Three coordinated fixes shipped today:

**Fix 1 — `{{badge_link}}` template variable** (`696568a`, 15:55 UTC)
  New template variable that resolves to
  `https://leena.app/badge-print.html?qr=<visitor uuid>` — a durable
  page URL that Yaprak drops into templates as an "if you can't see
  the QR" fallback. Live at all three render sites: `email_worker.js
  :225-231, :249`, `routes/visitors.js:375, :387` (public form), and
  `routes/visitors.js:864, :872` (import existing-visitor email).
  `{{qr_code}}` behavior byte-identical.

**Fix 2 — fallback line inserted into 6 templates** (SQL, run
  in-flight via Render Shell using the G47 staged-payload pattern)
  Templates 28 (SIEMA Exhibitor), 47 (SIEMA Visitor EN), 69 (SIEMA
  Visitor FR), 86 (Madesign FR), 87 (Madesign EN), 88 (Madesign
  Exhibitor) received a bilingual fallback block immediately after
  `{{qr_code}}` in both `html_content` and `body`. Backup:
  `email_templates_backup_20260910` (6 rows).

  Scope narrowed to templates that DO NOT go through
  `routes/emailSend.js` (which builds `emailData` without
  `badge_link` — 14-day audit showed zero panel sends on these 6
  templates). Excluded templates are in the follow-up items on
  todo.md.

**Fix 3 — public badge page redesigned** (`2eee318`, 17:08 UTC)
  `public/badge-print.html` full-file rewrite (450 → 260 lines) —
  the URL `{{badge_link}}` points at is now customer-facing.
  Bilingual (EN/FR), mobile-first, neutral white-card theme
  consistent with the QR mails, shows the real expo name + dates +
  venue. Backend `routes/visitors.js:125-144` `GET /badge/:qr_code`
  SELECT expanded with `LEFT JOIN expos e ON e.id = v.expo_id` and
  7 new `expo_*` columns aliased in the payload. Zero auth,
  client-side QR render via jsdelivr qrcode@1.5.1 preserved
  (durable against `/api/qr-image` outage).

Combined effect: any recipient whose gateway strips the QR `<img>`
now has a working escape hatch to a professional per-visitor badge
page they can print or save as PDF.

## 4. Reply-parser bug — root cause confirmed and fixed

`routes/emailInbound.js:22-64` prefers `req.body.text` over
`req.body.html` over raw MIME. When SendGrid's Inbound Parse config
had "POST the raw, full MIME message" checkbox **ON**, `text` and
`html` were not populated — the code fell through to a manual MIME
split that emitted `=E7`, `=92`, `=C3=A9` quoted-printable entities
and multipart boundaries verbatim in [Visitor Reply] forwards.

**Suer flipped the checkbox OFF ~13:20 UTC.** SendGrid now pre-parses
and populates `req.body.text` on delivery. Zero code change required.

**Parser fix field-confirmed 17:12:47 UTC** — first post-fix
`[Visitor Reply]` forward arrived clean: reply to *"nabil atouf, votre
badge SIEMA 2026 est prêt"* rendered with **decoded French accents
(é, à, ê) and zero MIME residue** — no `=E7`, no `=92`, no `=C3=A9`,
no `--boundary_*` markers, no multipart headers. Same-day pre-fix
samples from 11:17 UTC still showed raw quoted-printable + multipart
boundaries verbatim.

Rule captured as G48 (permanent OFF).
